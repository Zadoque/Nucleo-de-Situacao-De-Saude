\section{Contexto geral do projeto}

O Núcleo de Situação de Saúde (NSS) tem como objetivo centralizar e analisar dados
públicos de saúde, com foco inicial em notificações do Sistema de Informação de
Agravos de Notificação (SINAN), disponibilizadas via biblioteca \texttt{PySUS}.
A partir desses dados, pretende-se monitorar possíveis surtos epidemiológicos,
apoiar a elaboração de planos de contingência, servir de base para pesquisas
acadêmicas e fornecer informações consolidadas para gestores públicos e para o
público geral.

Nesta sprint, o foco foi \textbf{estruturar o repositório}, \textbf{definir a
arquitetura de dados} (Bronze--Silver--Gold) e \textbf{preparar o esqueleto de
back-end e front-end} que serão evoluídos nas próximas iterações.

\section{Organização do repositório}

Antes desta sprint, o repositório GitHub estava vazio. Foram criadas as
seguintes estruturas principais:

\begin{itemize}
  \item \textbf{\texttt{README.md}}: arquivo principal de documentação do
        projeto, descrevendo objetivos, arquitetura, estrutura de pastas e
        instruções para executar o back-end e o front-end.
  \item \textbf{\texttt{back-end/}}: pasta dedicada à API e futuros serviços
        de back-end (FastAPI).
  \item \textbf{\texttt{front-end/}}: pasta dedicada ao dashboard web e
        protótipos de interface.
  \item \textbf{\texttt{Sprints/}}: pasta para documentação em LaTeX das
        sprints, facilitando o registro de decisões técnicas e evolução do
        projeto.
\end{itemize}

Essa organização reflete a separação de responsabilidades entre camada de dados,
API e visualização, e prepara o terreno para uma evolução incremental do
projeto.

\section{Arquitetura de dados (Medallion)}

Foi consolidada a adoção da arquitetura \emph{Medallion}, com três camadas
principais:

\subsection{Camada Bronze}

A camada Bronze é responsável pela ingestão bruta dos dados do SINAN via PySUS.
Cada execução produz um lote (\emph{batch}) armazenado em arquivos Parquet,
organizados por doença, ano de origem e metadados de ingestão. A estrutura
proposta segue o padrão:

\begin{verbatim}
bronze/sinan/
  disease=<doenca>/
    source_year=<ano>/
      ingestion_date=<data>/
        batch_id=<id>/data_<timestamp>.parquet
\end{verbatim}

Também é previsto um arquivo de metadados (\texttt{metadata.json}) contendo
informações como \emph{batch id}, quantidade de linhas, colunas presentes e
carimbo de data/hora da ingestão. Essa camada não realiza limpeza ou filtragem
significativa; seu papel é preservar o dado o mais próximo possível da fonte.

\subsection{Camada Silver}

A camada Silver é responsável por aplicar regras de limpeza, seleção de colunas
e normalização de códigos. As principais decisões desta sprint foram:

\begin{itemize}
  \item Selecionar, para o caso de uso inicial, as colunas:
        \texttt{DT\_NOTIFIC}, \texttt{SEM\_NOT}, \texttt{NU\_ANO},
        \texttt{ID\_MUNICIP}, \texttt{SG\_UF\_NOT}, \texttt{CLASSI\_FIN} e
        \texttt{EVOLUCAO}.
  \item Converter \texttt{DT\_NOTIFIC} para um tipo de data nativo, permitindo
        filtragem por ano, mês e janelas móveis (ex.: últimos 30 dias).
  \item Normalizar \texttt{ID\_MUNICIP} para um código IBGE de 7 dígitos,
        compatível com as malhas territoriais oficiais do IBGE.
  \item Normalizar \texttt{SG\_UF\_NOT} para um código numérico de UF de 2
        dígitos, mapeando para o nome/sigla correspondente.
  \item Criar colunas derivadas, como \texttt{MUNICIPIO} e \texttt{UF}, que
        facilitam a leitura por parte do usuário final.
  \item Definir chaves de deduplicação (por exemplo,
        \texttt{DT\_NOTIFIC}, \texttt{SEM\_NOT}, \texttt{ID\_MUNICIP},
        \texttt{SG\_UF\_NOT}) para remover notificações repetidas.
\end{itemize}

Os scripts existentes de Silver (fornecidos em arquivos separados) serão
integrados em futuras sprints dentro de uma estrutura de pacote Python,
aproveitando essa convenção de colunas e códigos.

\subsection{Camada Gold}

A camada Gold é responsável por produzir tabelas analíticas agregadas. Na
Sprint~1 foi definido o formato-alvo para suportar o dashboard de mapa de calor:

\begin{itemize}
  \item \texttt{disease\_code} -- código da doença (ex.: \texttt{deng}, \texttt{toxc}).
  \item \texttt{year} e \texttt{month} -- ano e mês de referência.
  \item \texttt{cd\_uf}, \texttt{nm\_uf} -- código IBGE e nome da unidade
        federativa.
  \item \texttt{cd\_mun}, \texttt{nm\_mun} -- código IBGE e nome do
        município.
  \item \texttt{cases\_total} -- quantidade de notificações no período para
        aquela combinação (doença, UF/município, ano, mês).
\end{itemize}

Os arquivos Gold serão salvos em Parquet em uma estrutura como:

\begin{verbatim}
gold/sinan/disease=<doenca>/year=<ano>/gold_cases.parquet
\end{verbatim}

Essa definição permite que a API responda rapidamente a consultas agregadas
por UF e por município.

\section{Back-end: esqueleto FastAPI}

Como parte da Sprint~1, foi criado um esqueleto de aplicação FastAPI no
 diretório \texttt{back-end/}, com o seguinte conteúdo principal:

\begin{verbatim}
back-end/
  app/
    __init__.py
    main.py
  requirements.txt
\end{verbatim}

O arquivo \texttt{requirements.txt} lista as dependências mínimas
(\texttt{fastapi}, \texttt{uvicorn[standard]}, \texttt{pandas}, \texttt{pyarrow}).

No arquivo \texttt{app/main.py} foi implementado:

\begin{itemize}
  \item Configuração básica da aplicação FastAPI, com título e descrição
        compatíveis com o projeto NSS.
  \item Função utilitária para listar doenças disponíveis com base na
        estrutura de diretórios em \texttt{gold/sinan/disease=*}.
  \item Função utilitária para carregar os arquivos Parquet da camada Gold
        para uma doença específica.
  \item Endpoint \texttt{/health}, que retorna o status de saúde da API.
  \item Endpoint \texttt{/diseases}, que lista as doenças presentes na camada
        Gold.
  \item Endpoint \texttt{/heatmap/uf}, que agrega a tabela Gold por UF
        (colunas \texttt{cd\_uf} e \texttt{nm\_uf}) e soma a coluna
        \texttt{cases\_total}, com parâmetros opcionais de \texttt{year} e
        \texttt{month}.
  \item Endpoint \texttt{/heatmap/municipios}, que agrega por município
        (colunas \texttt{cd\_mun} e \texttt{nm\_mun}) e também aceita filtros
        de UF, ano e mês.
\end{itemize}

Esses endpoints ainda assumem que a pipeline Gold irá produzir colunas com
nomes padronizados (\texttt{cd\_uf}, \texttt{nm\_uf}, \texttt{cd\_mun},
\texttt{nm\_mun}, \texttt{year}, \texttt{month}, \texttt{cases\_total}), o
que será implementado em sprints futuras.

\section{Front-end: protótipo de dashboard}

Na Sprint~1 foi criado um protótipo mínimo em HTML/JavaScript no diretório
\texttt{front-end/}. O objetivo é validar a comunicação com a API antes de
partir para um framework mais complexo.

O arquivo \texttt{index.html} contém:

\begin{itemize}
  \item Um pequeno formulário para seleção de doença (por enquanto
        \texttt{deng} e \texttt{toxc}), ano e mês.
  \item Uma chamada \texttt{fetch} ao endpoint \texttt{/heatmap/uf} da API,
        exibindo o retorno em uma tabela (colunas: código da UF, nome da UF e
        número de casos).
  \item Estilização simples em CSS para tornar a visualização mais agradável.
\end{itemize}

O arquivo \texttt{front-end/README.md} documenta como executar o protótipo
utilizando um servidor HTTP básico (por exemplo, \texttt{python -m http.server}).

Embora o mapa de calor propriamente dito (com malhas do IBGE e coloração por
intensidade) ainda não tenha sido implementado, este protótipo já estabelece a
integração back-end/front-end e serve como base para evoluções futuras.

de evolução do projeto.

\section{Resumo da Sprint 1}

De forma resumida, a Sprint~1 entregou:

\begin{itemize}
  \item Organização inicial do repositório GitHub com separação clara entre
        back-end, front-end e documentação de sprints.
  \item Definição da arquitetura de dados baseada em camadas Bronze, Silver e
        Gold.
  \item Esqueleto funcional de API FastAPI com endpoints para saúde da API,
        listagem de doenças e agregações por UF e município.
  \item Protótipo estático de front-end consumindo o endpoint de UF.
  \item Estrutura de documentação em LaTeX para registrar decisões técnicas e
        planejamento.
\end{itemize}

Esses elementos criam uma base sólida sobre a qual será possível avançar para a
implementação completa da pipeline de dados, do dashboard com mapa de calor e
de funcionalidades adicionais em sprints futuras.
